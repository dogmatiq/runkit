# 12. gRPC

Date: 2026-05-03

## Status

Proposed

> [!NOTE]
> This decision has not yet been accepted and is subject to change.

- References [5. Homogeneous cluster nodes][ADR-5]
- References [7. Node heartbeat][ADR-7]
- References [11. Mutual TLS][ADR-11]

## Context

Every node runs all engine components and communicates directly with every peer
([ADR-5]). Each node publishes a network address in its heartbeat record that
its peers use to dial it ([ADR-7]).

Inter-node traffic has varied communication patterns — some request/response,
some requiring the server to push data to the client. All connections are
direct and secured with mutual TLS ([ADR-11]).

## Decision

We will use [gRPC] — specifically the canonical [`google.golang.org/grpc`]
implementation — as the inter-node RPC framework. Three properties make it
well-suited to the communication model:

- **Bidirectional streaming.** gRPC natively supports server-push and full
  bidirectional streaming, covering the full range of communication patterns.
- **Connection management.** gRPC provides keepalive, transparent reconnection,
  and multiplexing of all service calls over a single underlying connection per
  peer, with no custom framing code required.
- **Mutual TLS.** gRPC's `credentials.TransportCredentials` interface is the
  integration point for the pluggable credential strategies established in
  [ADR-11], making them straightforward to wire into connection establishment.

### Dismissed alternatives

- **Custom multiplexed transport (yamux, smux, raw TCP)** — full control over
  framing, but ownership of keepalives, flow control, and credential integration
  is required; gRPC provides all of this at no implementation cost.
- **Embedded [NATS]** — eliminates direct dialing between peers, but introduces
  a message broker dependency solely as a transport layer. The cluster already
  commits to direct peer-to-peer connections; adding a broker is unjustified
  complexity.
- **[ConnectRPC]** — wire-compatible with gRPC over HTTP/2 and uses standard
  `net/http` handlers, which simplifies middleware integration. However, it
  offers no meaningful advantage over gRPC for internal peer-to-peer traffic
  where browser compatibility is irrelevant.
- **[Server-sent events][SSE]** — server-to-client only; bidirectional
  communication requires a separate reverse connection per peer pair. Text-based
  framing also forces base64 encoding of binary protobuf payloads.
- **[WebSockets]** — full-duplex binary messaging, but no multiplexing or
  request/response structure. Multiplexing concurrent RPCs over a single
  connection requires building an application-level protocol on top, approaching
  the complexity of a custom transport.

## Consequences

Each node holds one open connection per peer at all times. A broken connection
is immediately observable — rather than waiting for a heartbeat record to
expire, a node can detect peer unreachability as soon as the connection drops.
The connection acts as a real-time presence signal that complements the
authoritative liveness signal in the heartbeat store ([ADR-7]).

Authentication occurs at connection establishment via mTLS ([ADR-11]), not
per-RPC. Once the handshake succeeds, all RPCs on that connection are implicitly
trusted as the authenticated peer.

The engine already needs a gRPC server to implement `enginekit`'s event stream
consumption API. This ADR reuses that dependency for all intra-cluster traffic
rather than introducing a second transport.
